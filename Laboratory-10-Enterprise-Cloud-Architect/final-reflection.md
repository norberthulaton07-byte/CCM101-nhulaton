
The error “Unable to locate package docker-compose-plugin” appeared first, and soon after we found that the docker command, the docker group, and the service itself were all missing. It felt like four separate failures. Looking back, it was one: Ubuntu’s default repositories don’t carry that package, so the installation never happened. Once we added Docker’s official repository, everything fell into place together. The lesson I took from this is to stop and ask what single thing could explain all the errors before fixing them one by one. A smaller mistake taught me something similar. A “No such file or directory” error happened only because we had logged back in and were in the wrong folder. Now I check where I am in the terminal before I suspect anything else.
We enabled UFW and assumed the server was protected, but Docker writes its own network rules and can publish container ports without UFW ever being consulted. We proved it by running a test container on port 9090, which was reachable even though UFW had not allowed it. After applying the Docker firewall fix, the same test was blocked. Seeing it fail and then work made the lesson stick: security tools can’t be trusted just because they are switched on. You have to know how the other tools on the machine interact with them, and then test.
This lab also showed me how connected our work was. The deployment needed the VM’s IP address, the firewall needed the correct ports opened, and the backup script needed the exact name of the database container. A wrong detail in one person’s part could break another’s, so we kept sharing updates and confirming details with each other.
