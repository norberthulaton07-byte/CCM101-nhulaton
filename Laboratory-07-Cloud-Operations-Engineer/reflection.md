# Mission Reflection

Before doing this lab, I assumed that if a container was running, everything was fine. I learned that this isn't always true. Checking the host server's resources matters because every container depends on the machine underneath it. A container can look perfectly healthy while the server itself is quietly running out of memory or disk space. Containers share the same RAM, CPU, and storage, so one problem on the host can slow down or crash everything running on it. That is why I checked the baseline first, so I knew what normal looked like before a traffic surge could expose a weakness.

The second question is about a user who cannot log into a web application. In that situation, I would run `docker logs` on the container first. Logs record every request the application receives, along with the status code it returned. If the login request shows a 500 error, I would know the problem is on the server side. If it shows a 404, the login page may be missing or the URL may be wrong. In this lab, the 404 line from my hidden-admin-page request showed exactly what was asked and when. Instead of guessing, I could follow the evidence to the cause, which is a much faster way to fix a problem.

Logs and metrics are not the same thing, even though both help with monitoring. Logs are a record of events, like a diary that tells the story of what happened: who asked for which page and what the server answered. Metrics are numbers that describe health at a given moment, such as CPU percentage, memory usage, and network traffic from `docker stats`. Logs help me understand why something went wrong, while metrics help me notice that something is wrong, or about to go wrong. Together they give a complete picture, and I now see monitoring as a habit that keeps small problems from becoming outages.
