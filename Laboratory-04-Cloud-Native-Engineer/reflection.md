# Mission Reflection

Deploying a Docker container turned out to be far faster than installing an operating system on a Virtual Machine. Setting up a VM means installing a full guest operating system and then installing and configuring the web server, which can take fifteen minutes or more, on top of the minutes the VM needs to boot. With Docker, I pulled the Nginx image and started a working web server in seconds using only two commands. Because a container shares the host kernel instead of running its own operating system, there was almost nothing to boot or configure.
Port mapping is necessary because a container runs in its own isolated network, so port 80 inside it cannot be reached from the host by default. The -p 8080:80 option forwards traffic arriving on host port 8080 to port 80 inside the container. Without it, Nginx would be running, but curl http://localhost:8080 would fail because nothing on the host would be listening there. Similarly, I learned that the docker rm command deletes the container along with its writable layer, so any data created inside it is lost permanently. The original image is unaffected, so a new container can be started from it, but it begins fresh. To keep data such as logs or databases, I would need to use a Docker volume or bind mount.
Containerization also changes how developers and IT operations teams work together. A developer can package an application with all of its dependencies into an image, and operations can run that exact image anywhere, which reduces the classic problem of software working on one machine but not another. This makes deployments faster, scaling easier, and automation through CI/CD pipelines more practical, which supports a smoother DevOps partnership.
